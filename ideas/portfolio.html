Who these are for

P1The multi-profile tab hoarderhigh confidence
Today

Runs several Chrome profiles at once — personal, work, one per client, each with different logins — and holds far more tabs open than anyone can reason about. The scale is on record in the repo: one saved window holding 521 of 527 tabs. The app lets him look backwards at all of it beautifully, and gives him exactly one action to take on it.

Weekly ritual

Re-imports periodically, because the two archives are complementary — local Chrome expires at about 90 days while the Takeout export holds a full year. Browses research sessions and insights. Forwards links worth returning to into ThreadCrumb.

Frustration

Closing tabs, grouping tabs, or otherwise taking some action on the way-too-many-tabs that I have open at any given time. Also moving tabs across windows.

P2The “I know I read this” searcherproblem-space
Today

Types a half-remembered phrase into the browser's history box and gets what one commenter called “the same barely searchable table of URLs as their only history view.” The phrase they remember is from the body of the page, not its title — so title-and-URL search cannot find it. They fall back to a search engine, or hand-roll: one built a local logging proxy feeding a Django app; another pastes raw SQL from their dotfiles.

Frustration

Is there any product out there that creates a fully searchable full-text history forever with little fuss?

Ask HN, 235 points / 83 comments. The same author rejected the leading alternative for requiring you to save first: “My brain, naturally, does not know ahead of time what could be useful in the future.”

P3The local-first refugeeproblem-space
Today

Has been burned. Memex removed its licence and confirmed it was no longer intended to be open source — and a user in that thread said being free software “was the main reason I chose to use Memex.” Falcon, still the tool people recommend to each other, has not been pushed since August 2024. One competitor drew a two-word review: “Subscription fatigue.”

Frustration

There is no durable winner, and no way to audit what a tool actually sends outward. The first question asked, every time, before any feature discussion:

How and where is the full text of every page I visit getting stored & for how long?

Why each one survived

The kill-question answers that decided the verdict, and the honest scope note attached to each.

01Keep the page text you already fetch, and search itAdvance
Unique leverage

Structural, not incremental. Every extension-based competitor is bounded by browser storage quotas — one analysis of Falcon's source flagged that page text was never truncated inside storage.local, and its maintainer cited the storage ceiling as the reason to decline sync. A server-side SQLite file has no such ceiling. This is the project's real advantage and it is currently unclaimed.

Does it duplicate anything?

No — it upgrades two things at once. Embeddings today are built from title + url truncated to 800 characters, so two pages both titled “Docs” cluster nowhere near their real topics. The FTS index covers title, URL, domain and path, and cannot answer “find the page that said this.”

Smallest credible version

Persist the extracted text as a new enrichment kind when summarizing, embed the text instead of the title, and add it as a fifth FTS column. No new dependency, no new fetch path, no new provider.

Scope note: depends on idea 12 for a durable full-history backfill. Storage grows meaningfully — roughly a few hundred megabytes at 30k pages — which SQLite handles comfortably but which should be a stated, opt-in cost rather than a surprise.
02Put liveness and transition into the ThreadCrumb captureAdvance
Unique leverage

A cross-source join nothing downstream could reproduce: the Graveyard already computes a liveness verdict for every checked URL, and an intent inbox has no way to derive that on its own. Forwarding it turns a relay into a triage signal.

Why now

The maintainer named deeper ThreadCrumb integration as the one feature only he would think of — and the repo's own engineering notes had already flagged this exact function as the deliberate place to shape what a history link becomes in an inbox.

Smallest credible version

One join in the existing capture query, two new fields in the context payload.

Scope note: “better integration” was deliberately under-specified in the interview, so the brief opens with what else this seam could carry rather than treating the two-field version as the finished answer. The ceiling depends on ThreadCrumb-side behavior this repository cannot see.
03Open tabs into the right Chrome profileAdvance
The problem

This is not a missing feature — it is a shipped feature that is actively wrong for its primary user. Reopening hands the URL to the operating system's default browser, so a client tab lands in whichever profile happens to be default, with the wrong logins.

Unique leverage

The app already detects profile directories in order to import from them. Nothing else on the machine knows this profile layout.

Smallest credible version

Invoke the browser binary with a profile-directory argument instead of the OS handler, keeping the current handler as the fallback for anything unresolved.

Scope note: hours of work, and the highest value-per-hour item in the portfolio for the maintainer specifically. Cross-platform profile resolution is the only fiddly part.
04Show what left the machine — an egress audit logAdvance
Unique leverage

The record already exists. Every outbound call — liveness check, summary, embedding — writes a row with a timestamp. It has simply never been shown to anyone.

Does it duplicate anything?

It completes the privacy feature rather than repeating it. Privacy rules state intent; this shows outcome. Idea 7 exists precisely because those two can diverge without anyone noticing.

Smallest credible version

A settings panel listing hosts contacted, by which path, when — with a count of what was skipped for being private or hidden.

Scope note: the differentiation claim is real but unproven — no comparator offers this, and no user has explicitly asked for it in these words. The demand evidence is that local-first users ask the underlying question first, before features.
05Import bookmarks as a first-class sourceAdvance
Demand

The highest-reacted open request on the closest feature-matched comparator, verified at 8 reactions. One commenter there: “I have bookmarks going back to 2009... Sadly, many of the links are now dead. I wish bookmarking had saved copies of these pages.” Corroborated by a second tracker.

Unique leverage

Bookmarks crossed with the existing dead-link Graveyard answers exactly that comment — “this thing you deliberately kept is gone” — which no comparator can currently say. The transition vocabulary already includes a bookmark type; the entity is what is missing.

Scope note: effort is uneven across browser families and this should be verified before committing. Firefox bookmarks live in the same database the adapter already opens; Chromium keeps them in a separate JSON file entirely. Firefox first is the honest sequencing.
06Render saved windows as the navigation tree they wereAdvance
Unique leverage

The referrer column is the actual parent edge between pages. Research sessions today infer structure from time-adjacency plus a count of link-type transitions — a flat trail where a tree was recorded. Both columns are written at ingest and never read.

Demand

Recurring in the research: one commenter wanted “a view that reflects tab histories as some kind of graph”; another described wanting to see “trails as tree instead of tabs.”

Scope note: this is Takeout-only. Local browser imports expose no session data at all, so a local-only importer never sees this feature. That materially caps its reach and is the main argument against sequencing it early.
07Close the hidden-host liveness gapAdvance
What was found

The two privacy flags are computed independently, so a host matched only by a Hide rule is marked hidden but not private. All three liveness batch scopes filter on private only. The result: scoped liveness checks issue outbound requests to hosts the user asked the app to hide.

Why it reads as an oversight

Every other outbound path gates correctly — AI, clustering, ThreadCrumb, insights, statistics, the domain tree. Liveness is the lone exception.

Scope note: this is a decision, not just a fix. The README says hidden hosts are never sent to liveness; the security policy says only that hidden hosts are excluded from every view. The code matches the security policy. Tightening the code and narrowing the README are both valid resolutions, and choosing between them is the maintainer's call.
08Let every view export what's on screenAdvance
The asymmetry

Four distinct import paths; zero export paths. No CSV, no download endpoint, no content-disposition header, no blob or download attribute anywhere in the client — confirmed by grep across the whole repository. There are no delete routes either.

Unique leverage

The artifacts worth exporting exist nowhere else: AI-named research sessions, k-means topic labels, liveness verdicts, the Graveyard. For a tool whose pitch is derived value, a one-way door is the conspicuous missing half.

Scope note: exports must honor the same read-time privacy filter the views already apply, so export inherits the privacy posture rather than re-deriving it. Catch-up rather than differentiating, but well-evidenced catch-up.
09Make Takeout importable from the Import tabAdvance
The gap

Takeout is the headline source and the only one carrying saved tab sessions — and it is the single source you cannot import from the interface. Every lesser source is two clicks away; this one is a terminal command. All the server-side pieces already exist; only the route shape blocks it.

Why now

Setup friction decides adoption in this niche — the top-reacted open issue on the healthiest comparator is, literally, a request to make it easier to run. This repository has just gone public, which makes the first five minutes matter more than it did last month.

Scope note: pure friction removal, no differentiation. Hours of work.
10Act on the tabs that are open right nowValidate
Demand

The strongest single piece of evidence in the run, stated directly by the only confirmed user this project has. The repository corroborates the scale independently: one saved window holding 521 of 527 tabs.

The asymmetry

The app has exactly one live-action verb and it only goes one way. Opening is fire-and-forget — nothing comes back, so the app can create tabs and can neither see, close, group nor move a single one.

Why Validate rather than Advance

It scores in the Advance band, but the implementation path is genuinely unresolved. A browser extension and a debugging-protocol client are different products with different install stories, different permission models, and different failure modes. Committing to a build plan would front-run that decision.

Scope note: the deliverable is a one-day spike that answers the architecture question and returns a recommendation — not an implementation plan. This is the one genuinely new-ground item in the portfolio, and the one most likely to change what the product is.
11Finish the three half-wired featuresAdvance
What is half-built

A per-URL visit timeline: endpoint built, typed client method built, called by no component. Stored AI summaries: bulk-fetch endpoint built, client method built, called by no component. And an import silently invalidates research sessions and the interest map, with nothing in the interface saying so — the maintainer's own code comment acknowledges there is no incremental path.

Direct cost impact

Because summaries are never read back, one generated yesterday is invisible today and re-clicking bills the provider again. Embedding persistence is sold in the README as a one-time cost per URL; summaries get the same durable storage and none of the payoff.

Scope note: scores in the Validate band but lands at Advance, because there is nothing to validate — this is completion work over code that already exists, with no open questions. Recorded rather than silently promoted.
12Generalize the enrichment queue past livenessAdvance
The risk today

Embedding a full history loads every public URL and awaits the provider in chunks of 100, sequentially, inside a single HTTP request, against a 60-second idle timeout — roughly 300 round-trips on one connection at this database's size. It writes completion status directly, bypassing the durable queue, so a failure partway through loses the progress.

Unique leverage

The fix is already written. Crash-recoverable job machinery exists — status column, stuck-job reset at boot, a worker pool draining pending rows — and is artificially narrowed to one job kind in six places.

Scope note: infrastructure, not a user-facing feature, and it displaces user-facing work. It earns its place by unblocking idea 1 and removing a real data-loss risk that exists today. Progress bars and resumability come free once the queue is parameterized.
